# 为什么这里的上下滑动这么跟手

> 配套代码：`Sources/Core/PadGesture.swift`、`Sources/Core/RemoteControl.swift`、
> `Sources/ExternalDisplay/DisplayScrollGeometry.swift`、`Sources/App/GesturePad.swift`、
> `Sources/App/TouchSurface.swift`
>
> 相关章节：README 第四节（交互：外接屏收不到触摸）、第九节（瀑布流 + 下拉露背景墙）

## TL;DR

这种"跟手"不是调参调出来的，而是**架构上不存在那几件会拖后腿的事**：

| 体感 | 成因 |
| --- | --- |
| 手指停在哪，内容就停在哪 | 位移逐帧直连，中间没有动画插值 |
| 起手不跳 | slop 内的位移被吃掉，不补发 |
| 单指移光标时画面纹丝不动 | 光标与滚动按**手指数量**分流，不靠位移方向去猜 |
| 拖 1 秒和拖 2 秒一样"快" | 用的是累计位移**之差**，不是累计位移本身 |
| 斜着划也能滚 | 横向分量忽略但不拦截 |
| 换块屏（4K / letterbox 小窗）手感不变 | 存归一化进度，不存像素位移 |
| 越顶下拉手感自然变沉 | 阻尼曲线 `1 - (1 - t)^1.7` |
| 回拉不会凭空多滚一段 | 滚动与下拉共用**同一个**权威标量 |
| 滚动时没有卡顿 | 位移是纯变换，布局值一个都没变；星海按需暂停 |

**但有一件事要先说清楚：这里没有惯性。** 手指离开屏幕，内容立刻停住。
详见最后一节 —— 这是刻意取舍的结果，不是没做完。

---

## 一、一次手指移动经过什么

```
手指移动 / 落下第二根 / 抬起一根
      │
      ▼
TouchSurface（UIKit：透明 UIView 的 touchesBegan/Moved/Ended）
      │  全部手指的落点 + 时间戳     ← 不是"第一根"，也不是累计位移
      ▼
PadGesture（纯状态机，不认识 SwiftUI / UIKit）
      │  [.pointer(点), .scroll(归一化增量), .tap]
      ▼
RemoteControl（@Observable 单例，手机端与外接屏同进程）
      │  position: 0 → 1 滚动 / 0 → -0.9 下拉
      ▼
ExternalDisplayRootView
      │  .offset(y: pullOffset - scrollOffset)   ← 就这一行
      ▼
外接屏上的像素
```

链路只有五跳，而且**中间没有一跳是异步的**。

对比一下原生：UIKit 的 `UIScrollView` 内部是一整套滚动管线 —— 手势识别器、减速动画、
橡皮筋回弹、`contentOffset` 的动画插值、`scrollViewDidScroll` 回调里的布局失效。
每一段都值得，但它们叠在一起就是"手指动了之后、内容过一会儿才到"的那点延迟感。

这里没有那套管线，所以也没有那点延迟。

## 二、七条机制，逐条说

### 1. 没有 `UIScrollView`，位移就是一行 `.offset`

外接屏的 role 是 `windowExternalDisplayNonInteractive`，它**收不到任何触摸** ——
所以那里本来也挂不了 `ScrollView`（挂了也没人能滚）。

这件事反过来成了优势：滚动位置从一开始就是一个**可编程的标量**，
不用和 UIKit 的 `contentOffset` 抢夺所有权。

```swift
.offset(y: plan.scroll.contentOffset(scroll: remote.scroll, pull: pull))
```

### 2. 位移逐帧直连，中间没有动画

那行 `.offset` 上**没有** `.animation(...)`，也没有 `withAnimation`。

这不是漏写。加一层隐式动画，SwiftUI 会在"手指给的新值"和"上一帧的值"之间插值 ——
插值本身要时间，于是手指已经停住、内容还在慢慢追。表现就是"有一点点黏"。

去掉插值，内容就是手指的**逐帧镜像**。60 Hz 下每 16.7 ms 更新一次，
比任何缓动曲线都更像"东西在手里"。

> 全屏唯一带 `.animation` 的地方是 hero 图案的缩放（`zoom`，0.15 s `easeOut`）——
> 那是"封面图缩放"，本来就该有点余韵，与滚动无关。

### 3. slop 被吃掉，不补发

手指按下之后不会立刻滚动。位移得先越过 `slop`（8pt）才进入拖动状态：

```
按下 ──┬─ 没越过 slop 就抬起 ──▶ 轻点（点击确认）
       └─ 越过 slop ──────────▶ 拖动（开始滚动）
```

越界那一帧的关键动作是**把当前位移记成基准**，也就是把 slop 内积攒的那几 pt 丢掉：

```swift
if phase != .dragging {
    phase = .dragging
    lastTranslation = translation        // ← 吃掉 slop，不补发
    return actions
}
```

补发会怎样：手指动了 9pt 才越过阈值，那一帧就把 9pt 一次性交出去 ——
画面"咔"地跳一下。丢掉它，起手就是平滑的。

而轻点能成立，恰恰是因为`touching`阶段**从不产生滚动**：
若改成"一开始就滚、抬起时再补一次点击"，每次轻点都会顺手把画面推走几个点。

### 4. 增量 = 相邻两帧锚点之差，不是"从按下到现在的总位移"

`DragGesture.translation` 是**累计**值；直接拿它当增量，滚动速度会随拖拽时长线性放大 ——
拖 1 秒滚 1 屏、拖 2 秒滚 3 屏，手指明明没加速，内容却越跑越快。

现在喂进来的是**手指当前落点**（多指时是质心），状态机自己留上一帧的锚点，每帧算差：

```swift
let delta = CGSize(width: anchor.x - lastAnchor.x, height: anchor.y - lastAnchor.y)
lastAnchor = anchor
```

锚点在换手指数时会**跳**（两指质心 → 剩下那根手指），所以那一帧要整个吃掉、
并把死区重开。否则这一跳会被当成位移交出去 —— 表现是"抬起一根手指画面窜一下"。

这条写错的话，手感不一定"感觉慢"，也可能"感觉飘" ——
而两种表现都很难反推到"分母错了"这个原因上。

### 5. 存归一化进度，不存像素

`RemoteControl` 里没有"滚了 320 个点"这种量，只有 `0...1` 的进度。

外接屏可能是 4K、1080p、也可能是模拟器里 362×203pt 的 letterbox 小窗口，
尺寸差一个数量级。存归一化值，实际位移由外接屏按**自己的**内容高度换算：

```swift
var maxOffset: CGFloat { max(0, contentHeight + inset * 2 - viewport.height) }
func scrollOffset(for scroll: CGFloat) -> CGFloat { maxOffset * clamp(scroll) }
```

于是 `scroll = 0.5` 在哪块屏上都是"滚到一半"，手感与屏幕尺寸无关。

### 6. 滚动与下拉是同一个标量的两段

"往上滚"和"到顶了还继续往下拽"看起来是两个维度，实际是**同一条数轴的两段**：

```
position > 0  →  正常滚动进度（0 = 顶部，1 = 底部）
position < 0  →  顶部下拉的超出行程
```

对外仍暴露 `scroll` 和 `pull` 两个属性（渲染侧关心的是两件事），
但**唯一权威只有 `position`**。

为什么这点决定手感：如果拆成两个可独立写的字段，下拉时被阻尼吃掉的那部分行程，
在回拉时会变成"凭空多出来的滚动" —— 手指一松，内容就跳。

下拉的阻尼曲线也是在这里生效的：

```swift
static func progress(raw: CGFloat) -> CGFloat {
    let t = min(raw / rawLimit, 1)
    return 1 - pow(1 - t, exponent)      // exponent = 1.7
}
```

`t = 0` 处导数是 1.7，起手轻快；越接近 1 导数越小，末段发沉。
而且它在 `t = 1` 处**恰好等于 1**（不是渐近逼近）——
所以"拉到底，内容顶边正好落在屏幕中线"这个几何承诺是精确成立的，不会永远差一截。

### 7. 滚动不触发布局，星海也不添乱

滚动只改 `remote.scroll` 一个数。它影响的是：

- `.offset(y:)` —— 纯几何变换，**不参与布局**；
- `StarfieldBackdrop(dolly:)` —— 但星海只在**任一位移轴非零**时才走 `TimelineView`，
  正常滚动（三轴全零）时它一帧都不画。

> 星海现在是**常驻可见**的（幕墙半透，缝里看到的就是它），停帧判据因此从
> 「露出来没」改成「动没动」：静止时暂停重绘、保留最后一帧，画面照旧，
> 帧成本回到 0。代价是静止时星星不闪。详见 `docs/devnotes/2026-09-24-glass-wall-material-back.md`。

`WaterfallLayout.make(...)` 确实每帧都会重算一遍（它在 `body` 里的 `DisplayPlan` 中），
但它是 `O(n·k)`、n = 36、k = 4 的纯函数，而且**结果逐帧相同** ——
SwiftUI 比较之后认为 `WaterfallColumnView` 的输入没变，不会重排那 36 张卡片。

所以一次滚动的实际代价是：一次 `.offset` 的合成。没有布局、没有按需创建、
没有 `Lazy*` 容器在滑动中"临时建视图"的那种抖动。

> 代价在别处：36 张卡片是**一次性**全建出来的（外接屏用不了 `ScrollView`，
> 也就没有 `LazyVStack` 的按需创建）。上百张的时候这里得自己写回收池。

## 三、手势归属靠结构，不靠运气

触控板最初放在 `Form` 里，它的 `DragGesture` 会和外层滚动视图的竖向 pan 手势打架 ——
而 SwiftUI **没有**能压过祖先 `ScrollView` 的公开 API（`highPriorityGesture` 只影响
当前视图与其子视图）。

现在采集面由 `RemoteControlDock` 经 `.safeAreaInset(edge: .bottom)` 挂在滚动区域
**之外**，归属没有歧义。

换成 UIKit 触摸层之后这条约束只会更硬：祖先 `ScrollView` 的 pan 识别器一旦认可，
会直接给采集视图发 `touchesCancelled`。手势竞争至少还能看到"两个都想抢"，
这个连报错都没有，表现就是拖动中途突然停住 —— 所以它同样必须待在滚动区域之外。

另外两个刻意为之的细节：

- **横向分量忽略，但不拦截**。斜着划照样能滚，只是横向那段不产生位移。
  若改成"只认纯竖向拖动"，斜拖会被判成手势失败，手感立刻变粘。
- **落点映射不设 slop**。`slop` 只约束滚动；光标在手指一动就跟着走 ——
  光标本来就该跟手，等 8pt 才动反而怪。

## 四、这些手感是有断言的

`PadGesture` 是**纯状态机**，不认识 SwiftUI，所以"手指按下 → 产生什么动作"
这半条链路可以喂事件断言。目前 27 条，覆盖：

- slop 边界（5pt 算轻点 / 越过 slop 的那一帧不补发）
- 轻点判定（≤ 0.4 s、拖出去再拖回原点不算轻点、手势被取消不算确认）
- 逐帧增量（粗采样与细采样的总滚动量只差一个死区、滚动总量不超过实际位移）
- 方向（上滑产生负增量）、横向不拦截、开关（`mapsPointer` / `isScrollEnabled`）

`simctl` 没有触摸注入 API，所以"手势能不能被识别到"这最后一层（SwiftUI 的手势分发本身）
仍然只能手点；但**判定逻辑**本身是可回归验证的。

`PullCurve` 的逆函数往返恒等、端点、单调性也各有断言 ——
滑杆拖到底必须落在承诺位置上。

## 五、没有的东西：惯性

手指离开屏幕，内容立刻停住。**没有惯性滑动，也没有橡皮筋回弹。**

这是"没有 `UIScrollView`"的直接代价：UIKit 的减速动画是滚动管线的一部分，
不走那条管线就也没有它。

要不要补，取决于这块屏的定位：

- **不加**：指针/遥控式的浏览体验，指哪停哪，不需要"甩一下滑很远"。
  而且有了惯性之后，"到顶了还继续拽"这个下拉手势需要额外区分
  "手指拖出来的位移"和"惯性冲出去的位移"，`position` 单一标量的模型会变复杂。
- **要加**：在 `RemoteControl` 里加一层速度估计（抬手时取最近几帧的增量均值），
  再用 `CADisplayLink` / `TimelineView` 按指数衰减推进 `position`。
  衰减系数与停止阈值都需要实测调，且要和 `maxOffset` 的夹取配合 ——
  撞到顶/底要么硬停、要么回弹，两套手感得分别验。
  加完之后，"轻点"的判定不受影响（它走的是 `PadGesture`），
  但"拖动中途抬手"的语义会变，断言要跟着补。

---

## 六、一句话总结

原生滚动视图把"手势、减速、回弹、布局失效"打包在一起给你 —— 省事，代价是
你没法完全控制每一帧。

这里反过来了：因为外接屏本来就收不到触摸，滚动被迫退化成一个**可编程的标量**，
于是每一帧都由我们显式决定。跟手不是优化来的，是**没有中间层**的自然结果。
