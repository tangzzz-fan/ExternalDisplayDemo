# 瀑布流：左右边距 + item focus

分支：`main`
日期：2026-09-24
基线：`main`（左右出血版本）

## 缘起

两条需求：

1. **取消左右出血**。原先是 `horizontalBleed = base × 0.093`（1080p 上 ≈ 100pt），
   内容向两侧各溢出、最外两列被屏幕边缘切开。改成正常的左右边距：
   item 之间、以及屏幕左右两边都要有留白。
2. **item focus**。触控板 / 激光空鼠模式下，指针落进某个瀑布流卡片的范围时，
   该卡片要有 focus 效果（外围加环 + 阴影）。分「选中 / 未选中」两态。

第 1 项先落地，第 2 项见第二节。

---

## 一、左右出血 → 左右边距

### 改了什么

| 位置 | 之前 | 之后 |
| --- | --- | --- |
| `WaterfallMetrics` | `horizontalBleed = base × 0.093` | `horizontalInset = base × 0.07` |
| | `columnFieldWidth = viewport.width + bleed × 2` | `= max(0, viewport.width − inset × 2)` |
| `WaterfallColumnView` | 双 frame：排布区比视口宽、居中**溢出** | 双 frame 保留，改为居中**内缩** |
| `ExternalDisplayRootView.hero` | `.padding(.horizontal, inset)` | `.padding(.horizontal, horizontalInset)` |

`horizontalInset` 与竖向 `inset` **同源**（都是 `base × 0.07`）—— 这不是巧合，
是刻意取的：hero 与瀑布流共用同一条左右起始线，四个方向的留白也是同一个量级。

### 几何里没变的部分

双 frame 结构原样保留：

```swift
HStack { 各列 }
    .frame(width: metrics.columnFieldWidth, alignment: .top)   // 真实排布区，比视口窄
    .frame(width: metrics.viewport.width, alignment: .center)  // 对外仍宣称视口宽
```

外层那个 frame 仍然不是为了好看 —— 父级 `VStack` 拿到的宽度必须是视口宽，
否则容器会被撑宽（README 踩坑第 18 条）。**方向反了，这条约束不变。**

### 实测（三种视口）

列宽「前」是按旧公式回算的值，不是当时跑出来的读数。

| 视口 | 列数 | 列宽（前 → 后） | 两侧边距 |
| --- | --- | --- | --- |
| 1920×1080 | 4 | 512.6 → 424.4 | 75.6 |
| 1024×768 | 3 | 377.7 → 294.2 | 53.8 |
| 355×200 | 4 | 94.8 → 78.5 | 14.0 |

截图放大核对（`pull = 0`）：hero 的左右边缘与最外列的边缘**对齐**，两侧留白对称，
所有列完整落在屏内，没有任何一列被切成半个。

### 断言的变化

出血的 5 条换成边距的 6 条（脚本总数 162 → 166 条，全过）：

- 排布区宽 == 视口宽 − 两侧边距（原先：== 视口宽 + 两侧出血）
- 左右边距为正、排布区比视口窄（原先：出血为正、排布区比视口宽）
- 排布区左边缘内缩量 == 边距
- **新增**：最外列完整落在屏内 —— 这是这次改动的核心承诺
- **新增**：左右边距 == 竖向 `inset`（四边同源）

删掉的是「最外列仍有可见部分 ≥ 列宽 30%」—— 那条只在出血场景下有意义
（外列有一半在屏外，才需要卡"别只剩一条缝"）。现在列宽即完整宽度，这条恒真，
留着只会变成噪声。

### 踩坑

**1. `columnFieldWidth` 会变负。**

出血版是 `viewport.width + bleed × 2`，恒大于视口宽，不需要护栏。
改成正向之后，视口窄到装不下两侧留白时它会变成负数，而负数宽度传给 `.frame(width:)`
（SwiftUI 里是未定义行为），画面上的表现很难反推到"宽高比太极端"这个原因。
所以加了 `max(0, _)`：最坏情况列宽退化成 0，一眼看得出是宽度不够，而不是布局乱掉。

**2. 别把 hero 的左右内边距也换成竖向 `inset` 就完事。**

值相等、行为等价 —— 但语义不同。hero 与瀑布流必须取**同一个横向量**，
否则以后单独调其中一个，两边的起始线就错开了，而那种错位在截图上非常难被发现
（差的往往只有几个点）。

## 二、item focus

### 需求与两态语义

触控板 / 激光空鼠模式下，指针落进某张瀑布流卡片的范围时，该卡片要有 focus 效果
（外围加环 + 阴影）。分两态：

| 态 | 触发 | 表现 |
| --- | --- | --- |
| 悬浮 | 指针落在卡片上 | 细环（白）+ 柔光晕 |
| 选中 | 轻点 / 扳机确认 | 粗环（激光红）+ 浓光晕；再点同一张取消 |
| 未选中 | 其余全部 | **维持原样** —— 不加环、不加光晕 |

选中态**优先**于悬浮态：两张卡同时被指针和选中踩中时画选中那一种
（指针从已选中的卡上划过时，不该看起来像"掉了"）。

### 判定为什么只能在外接屏这侧算

外接屏收不到触摸（role 是 `windowExternalDisplayNonInteractive`），
光标位置由手机端经 `RemoteControl` 送过来 —— 而**几何只有外接屏知道**：

- 视口尺寸（1080p / 4K / letterbox 各不相同）
- hero 高度（由下拉几何反推出来的上限压低）
- 内容的滚动位移（每帧都在变）

手机端要用同一套判断，就得先把这三个量同步回去，然后再算一遍 ——
而它们本身又都依赖外接屏算出来的布局。绕一圈没有任何收益。

所以就地在渲染侧算，但**做成纯函数**：`WaterfallFocus`（`Sources/ExternalDisplay/`）
只吃 `CoreGraphics`，不认识 SwiftUI，于是可以在没有视图、没有模拟器的情况下跑断言。

### 几何：`placements`

命中需要每张卡的矩形，而 `WaterfallLayout` 原先只算高度（`heights`）不存坐标。
补上：

```swift
struct WaterfallPlacement {
    let id: Int
    let column: Int
    let frame: CGRect        // 相对**列排布区**左上角，不是视口
}
```

坐标系选列排布区而不是视口：排布区与屏幕之间还隔着左右留白（第一节刚改过），
把它挡在布局层之外，落位就只跟布局本身有关 —— 留白将来再调，落位不用动。

一处容易写错的地方：

```swift
columns[target].append(item)
columnHeights[target] += height
// 累计高度此刻**已经含**这一项，减掉才是它的顶边
placements.append(... y: columnHeights[target] - height ...)
```

顺序反过来就不会错得那么隐蔽（顶边会是上一项的底边），但那样少加了一次 `itemSpacing`。

### 两个平移量，来源完全不同

```swift
func item(at point: CGPoint, contentOffsetY: CGFloat = 0) -> Int?
```

- `fieldOrigin`（存在 `WaterfallFocus` 里）：列排布区左上角在**内容容器**里的位置。
  横向来自左右留白，纵向是「上内边距 + hero + VStack 间距」。
  它只在**视口尺寸变化**时重算。
- `contentOffsetY`（每次调用传进来）：内容容器随滚动 / 下拉的位移，**每帧都变**。

混在一起的话，"内容滚了"和"布局变了"这两件事在调用点上就分不开了 ——
而它们的更新频率差两个数量级。

命中用 `CGRect.contains`，它是**半开**区间（含 `minX` / `minY`，不含 `maxX` / `maxY`）：
相邻两张卡之间的那条边界只会归属其中一张，不会同时命中两个、也不会两边都落空。
卡片之间本来就不可能重叠（列内靠累计高度、列间靠列宽 + 间距），
所以最多命中一个，遍历顺序不影响结果。

### 选中状态为什么放在 `RemoteControl`

按原计划它是渲染侧的 `@State`，改掉了。理由是**验证能力**：

`simctl` 没有触摸注入 API，"点一下卡片"在自动化里做不到。状态留在 `@State`，
选中态就只能靠手点截图 —— 而 `-remoteState` 那套预置参数（`MockRemoteState`）
写的全是 `RemoteControl`，它照样碰不到视图内部的状态。

放进 `RemoteControl` 之后，`-remoteState pointer=0.3:0.4,selected=7` 就能一次截出选中态。

```swift
/// 本类里唯一一条「外接屏 → 模型」的写入，其余全部由手机端单向驱动。
private(set) var selectedItemID: Int?
func select(item id: Int?)
```

这是**刻意打破单向数据流**的一处：命中需要外接屏的几何，手机端无从判断，
所以只能由渲染侧算完写回来。写代码时留意这一条不要扩散 ——
`RemoteControl` 的定位仍然是"手机端驱动外接屏"，不是双向通道。

> 悬浮态**没有**入库。它每帧都可能变（空鼠 60 Hz），存进模型只会多出一份
> 要手动同步的副本，而它没有任何跨帧语义 —— 在 `body` 里现算即可。

### 视觉：环 + 光晕（不是投影）

```
悬浮：环  白 45%，宽 base × 0.006，离卡片 gap = base × 0.012
      晕  白 30%，radius base × 0.030
选中：环  激光红（LaserPalette.core），宽 base × 0.010，gap 同上
      晕  红 55%，radius base × 0.050 + 白 30%，radius base × 0.018
```

两个细节值得记：

**1. 黑色投影在近黑底上完全不可见。** 第一版写的是 `.shadow(color: .black, ...)`，
截图放大之后一点痕迹都没有 —— 卡片背后那层底是 `Color(red: 0.004, ...)`。
近黑底上唯一读得出来的"阴影"是外溢的**光**，所以两态都改成 glow，只换颜色与半径。

**2. 环画在卡片外面，圆角要跟着 gap 一起放大。**

```swift
RoundedRectangle(cornerRadius: cornerRadius + gap, style: .continuous)
    .strokeBorder(color, lineWidth: width)
    .padding(-gap)
```

只把矩形撑大而不动圆角，四角会出现肉眼可见的"两只角不平行"。
用 `strokeBorder` 而不是 `stroke`：前者画在形状内侧，尺寸正好是 `padding(-gap)`
撑出来的那一圈，不会再多占一个线宽。

**3. 环与光晕只画在命中的那一两顶上。** 做成条件分支，而不是"给所有卡挂一层
透明度 0 的阴影"—— 后者在 4K 上等于每张卡都多一个离屏合成图层，
36 张全静止也要付这笔钱。

### 实测

| 项 | 方法 | 结果 |
| --- | --- | --- |
| 落位与分列自洽 | 三种视口 × 8 条断言 | 列内恰好一个 `itemSpacing`、无重叠、落位底边 == 内容总高 ✔ |
| 命中判定 | 16 条断言 | 每项中心命中自己、边界半开、间距返回 `nil`、滚动位移后跟随 ✔ |
| 悬浮态 | `-remoteState pointer=0.15:0.63` 截图放大 | 卡片 01 外圈细白环 + 柔光晕 ✔ |
| 选中态 | 同参数 + `selected=1` | 红环 + 红光晕，遥控台读数「选中第 1 项」✔ |
| 空鼠模式 | `-mockAirMouse` 截图 | 指针扫过时环随卡片出现 ✔ |
| 纯函数断言 | `swiftc` 独立编译 + 运行 | **206 条全过**（166 → 206，新增 40 条） |

### 已知限制

1. **命中判定依赖 `fieldOrigin` 与 `contentColumn` 的布局结构手动对齐。**
   `fieldOrigin.y = inset × 2 + heroHeight` 是照着那个 `VStack(spacing: inset)`
   推出来的，两处改一处就会错位 —— 而错位的表现是"高亮在隔壁卡片上"，
   截图上看不出来（环确实画出来了）。当前靠纯函数断言守不住这条，
   因为它跨越了纯层与视图层。
2. **选中态不跟随内容变化。** 卡片被选中后滚动、卡片滚出视口，选中仍然留着。
   当前没有"选中项可见性"的处理。
3. **没有键盘 / 方向键导航。** focus 完全跟随指针，不存在"用方向键在卡片间移动"。
