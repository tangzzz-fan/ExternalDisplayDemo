# 触摸板双指滚动：把采集层从 SwiftUI 换到 UIKit

> 2026-09-24 · 分支级实验记录
>
> 相关：README 第四节（交互）、[`docs/scroll-feel.md`](../scroll-feel.md)、
> [`2026-09-24-airmouse-gesture.md`](2026-09-24-airmouse-gesture.md)

## 需求

触摸板（轨控板）模式下：

| # | 需求 | 来源 |
| --- | --- | --- |
| 1 | 双指滑动 → 滚动画面 | 用户 |
| 2 | 单指移动 → 只移光标，**不再滚动** | 用户 |
| 3 | 空鼠栏保持单指滚动不变 | 用户（"区别于激光空鼠模式"） |

即：**单指与双指各占一样，不再用位移方向去猜意图。**

---

## 一、为什么必须落到 UIKit

SwiftUI 在 iOS 17 上**拿不到手指数量**：

| 手势 | 拿得到 | 拿不到 |
| --- | --- | --- |
| `DragGesture` | 第 1 指的累计位移 + 落点 | **手指数量** |
| `MagnifyGesture` | 两指间距比 | 质心平移 |
| `RotateGesture` | 旋转角 | 与需求无关 |
| `SpatialEventGesture` | 多指事件流 | **要 iOS 18+**，本工程 target 17.0 |

而"单指移光标 / 双指滚画面"唯一的分辨依据就是手指数量。

### 那条"最小改动"路线为什么不成立

最初考虑的是：保留 `DragGesture` 管光标，另挂一个
`UIPanGestureRecognizer(minimumNumberOfTouches: 2)` 管滚动。

**不成立**。`DragGesture` 不知道有几根手指，双指滑动时它照样跟着第 1 指跑 ——
光标会在滚动的同时横着滑，正是需求 2 要消灭的行为。要压住它就得把触点个数报进
SwiftUI，而那一刻两套系统已经在抢同一批触摸，切换指数的瞬间光标会跳。

结论：那条路线省不掉 UIKit，只是少掉了"单一权威"这个好处，代码一行不少写。

### 为什么不用手势识别器

`UIPanGestureRecognizer` 只在自己认可之后才开始上报，**起手那段位移会被它吞掉**。
而那段位移在 `PadGesture` 里是要参与 slop 判定的 —— 吞掉之后"起手吃掉 slop"
这条纪律就落不到实处。所以直接读 `touchesBegan/Moved/Ended`。

### 三个必须记住的实现点

**1. `isMultipleTouchEnabled = true` 是那块视图的全部意义。**
默认 `false` 时 UIKit 默认只投递**第一根**手指，症状与"根本没写手势"一模一样，
而且不报任何错。少了这一行，整个文件白写。

**2. 上报必须用 `event.allTouches`。**
回调参数只带**本次变化**的手指 —— 第二根手指落下时参数里只有它自己
（`touches.count == 1`），状态机会误判成单指，于是"双指滚动"变成"光标被质心拽着走"。
要的是"现在一共几根"。

**3. 抬手指只在"一根都不剩"时才终结会话。**
两指下滑过程中先抬一根是常态，那一帧必须原样报出去（指数 2 → 1），
否则状态机看不到指数变化，质心那一跳会被算成一次位移。

## 三、状态机语义

| 场景 | 触控板（`.twoFinger`） | 空鼠栏（`.oneFinger`） |
| --- | --- | --- |
| 1 指移动 | 光标跟手，**不滚动** | 滚动 |
| 1 指轻点（≤0.4s 且位移 ≤8pt） | 选中 / 取消 | 扳机 |
| 2 指同步平移 | 滚动（取**质心**位移） | 按 1 指处理 |
| 2 指指距变化 | 不滚动（质心不动） | 按 1 指处理 |
| 指数变化 | 当帧零位移 + 死区重开 | 同 |
| 多指会话 | 光标与轻点**整段**关闭 | 同 |

两处细节值得单独说：

- **锚点取质心，不取"第一根手指"**。两指绕彼此转动时质心不动 —— 取第一根的话，
  一个纯粹的张开动作会被算成滚动。断言 `两指反向张开（质心不动）不产生滚动` 守这条。
- **多指判定用"本会话出现过的最大指数"（`peakCount`）而不是当前指数**。
  否则两指滑完抬起一根，剩下那根会把光标瞬间拽到自己身上。

## 四、指数变化为什么必须重设锚点

两指变一指时，锚点会从**两指中点**跳到**剩下那根手指**。断言里实测这一跳是 **+40pt**
—— 远超 8pt 的死区，漏出去就是一次可见的窜动（要么滚出去、要么把光标拽走）。

处理方式和"吃掉 slop"完全一样：**吃掉，不补发**。此外死区也重开 ——
换了手指组合就是换了手势意图。断言单独守了重开这件事：

```
指数变化后死区重开：质心走了 6pt、12pt 都还没产生位移
死区走完之后才开始产生位移
```

（这两条是**有区分度**的：若不在指数变化时清掉累计位移，第一帧就会越界。）

## 六、验收表（**必须手工过一遍**）

> `xcrun simctl` 没有触摸注入 API，「触摸到底有没有被 UIKit 收到」这一层
> **断言覆盖不到**。而且本机 Xcode 是精简安装（`…/Developer/Applications/Simulator.app`
> 不存在），模拟器 GUI 也起不来 —— 连半自动点击都做不了。

| 操作 | 预期 | 说明 |
| --- | --- | --- |
| 按住 **Option 拖动**（两指同步平移） | 画面滚动，**光标不动** | 需求 1 的判据 |
| **Option + Shift 拖动**（两指距离变化） | 只缩放，画面不滚 | 捏合仍归 `MagnifyGesture` |
| 单指直接拖 | 只有光标动，**画面不动** | 需求 2 的判据 |
| 单指轻点 | 选中 / 取消 | |
| 切到空鼠栏，单指上下拖 | 仍滚动 | 需求 3 的回归 |

**第一步先确认"有没有反应"。** 如果拖动完全没反应，先怀疑
`TouchSurface` 没收到触摸（命中判定 / `isMultipleTouchEnabled`），
而不是状态机 —— 状态机那半条有 223 条断言守着。

## 七、已知边界

- **真机未实测**：以上全部在模拟器上讨论。真机上的滚动手感、双指容差均未知。
- **捏合与双指滚动目前靠外部标志互斥**（`isMagnifying` → `isScrollEnabled: false`），
  不是真正的仲裁。两个手势同时满足条件时的行为依赖 `MagnifyGesture` 的
  `minimumScaleDelta: 0.01` 门限，未经压力测试。
- **滚动缩放没有惯性**（原本就没有，见 `docs/scroll-feel.md` 最后一节）。
