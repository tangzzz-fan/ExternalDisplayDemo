## 1. 先复核阶段 1/2 —— 以及一个差点误判的测量陷阱

阶段 1/2 交付时只跑通了断言与截图，**没有做过像素级复核**：墙体到底移了多少、
下沿落在哪一行，全靠肉眼看缩略图。这次补上，为此写了个探针工具
`.scratch/tools/probe.swift`：沿一条行/列扫描 PNG，把颜色相近的连续像素归并成「段」。

它立刻暴露了一个陷阱。

### 1.1 归并阈值把关键的那条边吞掉了

第一遍扫描 `bottom=1` 的截图，得到的是「墙从 y=663 一直延伸到窗口底边」——
也就是"墙根本没动"。差点就按这个结论去改代码。

真相是：**幕墙底色 `#020205` 与替身窗口底色 `#000001` 只差 1~2 个单位**，
而探针的归并阈值默认是 6。把墙的下沿连同它后面那片纯黑一起归并成了一段。

**阈值改成 1 之后，边立刻显出来了**：

| 状态 | 实测 | 理论 | 差 |
|---|---|---|---|
| `bottom=1` 墙下沿距窗口内容顶 | **95.0pt** | 视口高 195.6 × 0.5 = 97.8pt | 2.8pt |
| `lateral=1` 墙左沿距窗口内容左 | **52.7pt**（158px） | 短边 195.6 × 0.278 = 54.4pt | 1.7pt |

2~3pt 的残差与 4pt 的窗口边框、抗锯齿和边界归属口径有关，量级对得上。
**几何是对的。**

> 教训：这个项目里有一条"边界差 2 个单位"的真实情况（幕墙底 vs 近黑背景），
> 而它恰好是判据本身。任何"找边界"的自动化都必须用能分辨 1 个单位的阈值，
> 或者干脆逐点打印。阈值松的扫描会**给出一个自信的错误答案**，比报错更危险。

### 1.2 探针的用法

```bash
swiftc -O .scratch/tools/probe.swift -o .scratch/tools/probe
PROBE_TOL=1 .scratch/tools/probe shot.png column 603 600 1020   # 扫一列
PROBE_TOL=1 .scratch/tools/probe shot.png row 900 0 130         # 扫一行
             .scratch/tools/probe shot.png px 603 900           # 单点
```

配套的 `.scratch/tools/crop.swift` 负责裁出窗口区域（截图带手机 UI，直接看细节看不清）。

> 一个小坑：zsh **不做**无引号参数分词，`for p in "603 900"; do probe ... px $p; done`
> 会把 `603 900` 当成一个参数传进去（`Int("603 900") == nil` → 静默变成 0 → 退出码 2）。
> 循环里要显式写开，或者用 `${=p}`。

## 2. 阶段 3：材质 —— 反转三条既有决定

这是整个需求里唯一**与既有设计正面冲突**的部分。三条冲突都在代码注释里有据可查：

| # | 既有决定 | 出处 | 反转后 |
|---|---|---|---|
| 1 | 容器背景**必须不透明**："否则星海会从卡片缝隙里透上来，墙就立不住了" | `ExternalDisplayRootView` 的 `contentColumn` | 底板半透 58% —— 缝里透出来的正是星海 |
| 2 | 星海透明度由 `pull` 驱动，前 30% 淡入到位 | `StarfieldBackdrop.fadeIn` | **删掉**：星海常驻可见，透明度恒为 1 |
| 3 | 星海只在 `pull > 0.002` 时跑帧（"没露出来就不画"） | `StarfieldBackdrop.isActive` | 判据改成"**动没动**"（任一位移轴非零） |

第 1 条不是疏漏，是一条写进注释、有理有据的设计决定 —— 反转它意味着幕墙从
"挡住星海的墙"变成"浮在星海之上的玻璃板"。观感变化已由需求方确认接受。

第 2 条是第 1 条的必然推论：如果星海仍按 `pull` 淡入，**静止时列间缝隙里会是纯黑**，
需求 R6（透过 column 间隔看到星海）直接不成立。

第 3 条是代价的显式交换：星海从"交互时才可见"变成"一直在"之后，
"静止冻结"意味着**静止时星星不闪**。换来的是静止状态零帧成本
（600 颗星、约 60 条合并 Path、30~75 颗亮星各带一层径向渐变，4K 上不是小数）。

### 2.1 材质参数

```swift
enum WallMaterial {
    static let plateOpacity: Double = 0.58      // 底板
    static let cardFillOpacity: Double = 0.84   // 卡片填充
    static let plate = Color(red: 0.004, green: 0.005, blue: 0.014)
}
```

`plateOpacity` 是"缝里能不能看到星星"的唯一开关：`1` = 回到不透明（R6 不成立），
`0` = 卡片各自浮在星海里（"幕墙"不成立）。

`cardFillOpacity` **不能再低**：卡片上的编号与底栏文字是实心绘制的，
底面太透会让文字陷进星点里。**文字可读性优先于玻璃感。**

单独立一个类型而不是塞进 `LateralMetrics` / `ScrollMetrics`：那几个是纯几何、
只依赖 `CoreGraphics`，能被验收脚本直接编译；材质常量不该把它们拖进 SwiftUI。

### 2.2 为什么不做 `backdrop blur`

两条理由，任一条都足够：

1. **成本**：外接屏没有虚拟化，36 张卡一次性建出。每张挂一次 backdrop 采样 + 模糊
   = 每帧 36 次离屏合成，而背后的星海还在动。项目里连"给 36 张卡全挂透明度 0 的阴影"
   都被否过，理由同一条。
2. **方向相反**：需求要的是"看清后面的星星海"。模糊会把星点糊成雾。

玻璃感改由三样现成的东西撑：卡片已有的白描边、同侧径向高光、焦点环那套白环语言。

### 2.3 卡片半透的两个细节

**透明的是底，不是内容。** 封面渐变与底栏底各乘一次 `cardFillOpacity`，
而编号、底栏文案、白描边保持实心。若图省事对整张卡用 `.opacity()`，
文字会跟着一起淡下去，可读性先崩。

**底栏必须补一层同透明度的深底。** 底栏原本只有 `.white.opacity(0.05)`，
压在**不透明**的容器底上时看不出问题；底板一透，那 5% 白就变成几乎全透，
卡片下半段会比上半段透得多 —— 一块板上出现两种透光度，看起来像底栏漏画了。

## 3. 阶段 3 的另一半：曝光量

三条轴的位移方向各不相同，但"这块板离开原位多少"是一致的。投影强度、
四角圆角、星海的相机推进都该按它走。这个量从视图里提出来变成纯函数：

```swift
func wallExposure(pull: CGFloat, bottomPull: CGFloat, lateral: CGFloat) -> CGFloat
```

提出来是为了让"三向过卷 → 曝光量"这条规则进得了验收脚本 —— 留在视图的
computed property 里就是一个断言不到的黑洞。它同时**兼任星海的停帧判据**
（`exposure > 0`），于是"什么时候不跑帧"这条最容易写错的规则有了 10 条断言守着。

## 4. 阶段 4：返回按钮

### 4.1 为什么是浮动圆，不是一条栏

需求里有一条**明确的否命题**：按钮不能形成一条拦截的横线。

一条铺满屏宽的不透明栏会把幕墙切成两段：上沿露出的星海与幕墙本体被那条栏隔开，
看起来像两个不相干的区域。所以只垫一层 `black.opacity(0.35)`，
四周透出去的都是幕墙本身。

几何是纯函数 `BackButtonGeometry`：直径 = 短边 × 0.11，**外沿**距上/左边 =
短边 × 0.045（钉外沿而不是圆心 —— 人眼看到的是外轮廓到屏幕边的距离）。

### 4.2 命中按圆判，不是外接矩形

指针从四角划过时，矩形会在**视觉上根本没有按钮的地方**把点击吃掉。
断言里专门有一条钉它：外接矩形的角必须不命中。

### 4.3 命中优先级：按钮 > 卡片

这条不是"防御性编程"，是有**几何必然性**的：按钮在固定层（不随幕墙位移），
卡片在幕墙层（跟着位移）—— 于是必然存在"幕墙上拉之后卡片滑到按钮底下"的时刻。

断言里有一条把这件事钉住（用模拟器视口的真实几何算）：

```
静止时   按钮圆心落在 hero 区 → 卡片命中为 nil（不与卡片争同一片区域）
上拉到底 同一视口点 → 卡片命中非 nil（冲突真实存在，优先级因此必要）
```

同一条断言还有一个**反面**用途：防止以后有人觉得优先级多余而删掉它。

### 4.4 按钮的动作刻意留空

规格 §10.3 记录了原因：答复里"不做处理"是对"手机端要做什么"的回答（不用做），
而"跳转到星星海相册幕墙"描述的是**将来**的用途 —— 而那一页的内容规格并不存在。

所以：几何、命中、悬浮态全部实现并断言；点击只写一条 `lastEvent = "返回"`；
渲染侧的调用点唯一（`handleTap(in:)` 的第一个分支）。**不拿一个猜出来的页面顶上。**

## 5. 断言：257 → 303

新增 §10，46 条：

| 组 | 条数 | 要点 |
|---|---|---|
| 曝光量 | 10 | 三轴全零 → 0；单轴 = 该轴进度；`lateral` 取绝对值；多条轴取最大；上下限夹紧；负值按 0 处理；停帧判据 |
| 按钮几何 | 33（3 视口 × 11） | 直径与边距按短边缩放；不越出视口；圆心自命中；**外接矩形四角不命中**（圆≠矩形）；圆内/圆外两侧各一条 |
| 按钮 × 卡片优先级 | 3 | 静止时不与卡片重叠；上拉到底时冲突真实存在；同刻按钮命中自己 |

顺带修掉一处**常数重复**：`ExternalDisplayRootView.columnCount` 原本硬编码 `6`，
而验收脚本用 `WaterfallMetrics.columnCount(for:)`（自适应 3/4 列）算几何 ——
也就是说脚本断言的是**另一套列宽**。改成 `WaterfallMetrics.wallColumns = 6` 单一来源，
视图引用它、脚本也引用它。

## 6. 截图矩阵与实测

`-remoteState` 已支持 `lateral=` / `bottom=`（阶段 1 加的）。六个状态：

| 状态 | 命令 | 结果 |
|---|---|---|
| 静止 | （无 `-remoteState`） | 列间距与卡片四周**都能看到星点**（R6 ✓） |
| 右推到底 | `lateral=1` | 左侧露出一条星海；最右列被推出屏外（D6 批准的预期行为） |
| 左推到底 | `lateral=-1` | 对称 |
| 上拉到底 | `bottom=1` | 底部露出约半个视口的星海，墙体下沿圆角正确 |
| 下拉到底 | `pull=1` | 上半屏整片星海；**原几何承诺未被破坏**（回归 ✓） |
| 按钮悬浮 | `pointer=0.054:0.100` | 按钮环变粗变亮（悬浮态 ✓）；橙色光标环与之重合 |

按钮悬浮态的坐标是算出来的而不是试出来的：按 `margin + 直径/2` 得圆心
`(19.55, 19.55)` 点，除以视口 `362 × 195.6` 得归一化 `0.054 : 0.100`。

## 7. 已知限制（未验证的部分）

1. **触摸是否到达 UIKit** —— 仍然只能手过。`simctl` 没有触摸注入 API，
   本机 Xcode 是精简安装（没有 `Simulator.app`），模拟器 GUI 拉不起来。
   303 条断言盖的是"事件 → 几何 → 命中"，盖不到"手指 → 事件"。
2. **材质数值只在模拟器替身窗口（362×195.6 点）上看过。** `0.58` / `0.84`
   是按观感定的；1080p 真外接屏上星点更小更密，0.58 是否还合适没有证据。
   改这两个数是单点改动（`WallMaterial`）。
3. **静止时星星不闪** —— D6 的显式代价。要让它常闪就把 `isMoving` 传 `true`，
   但那等于让一块静止的屏永久付 600 颗星的绘制预算。
4. **相册幕墙那一页不存在。** 按钮的动作留空，等规格（见 §4.4）。
5. **1080p / 4K 上从未实测过**（本条与项目既有结论一致：本机只有模拟器）。
