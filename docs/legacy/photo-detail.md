# 照片详情页：整图 / 铺满、双击切换与拖拽

> 从瀑布流点一张卡进去，看到的是一张**照片**。默认完整可见，双击放大到铺满，
> 拖着看剩下的部分，再双击回来。手机端的遥控台全程不变 —— 换的只是同一个手指动作
> 落在哪个量上。
>
> 这一页是外接屏上**第一个有"页面"概念的界面**。在此之前，外接屏只画一屏幕墙，
> 没有"进入/退出"这回事。

---

## 一、口径：为什么不用「高度 fit / 宽度 fit」

需求最初的描述是「默认高度 fit，双击变宽度 fit」。对**横屏外接屏 + 横构图照片**，
这套说法与 `min` / `max` 缩放**完全重合** —— 所以在最初那个例子里它是对的。

换成竖构图照片（相册里的常态）它就不成立了：

| 场景 | 「宽度适配到底」的结果 |
| --- | --- |
| 16:9 视口 + 3:4 照片 | 高度变成视口的 **2.37 倍** |

用户看到的只剩中间一小段 —— 那不是"放大"，是失控。

所以口径改成两个**与照片形状无关**的模式：

| 模式 | 缩放 | 含义 | 横构图照片上的表现 |
| --- | --- | --- | --- |
| `fit`（整图） | `min` | 完整可见，不足的一侧留黑 | 高度贴边（= 需求说的 height fit） |
| `fill`（铺满） | `max` | 消除黑边，超出部分裁掉、可拖 | 宽度贴边（= 需求说的 width fit） |

对横构图照片，新旧两套说法**逐字等价**；对竖构图照片，新口径只是"铺满 + 可拖"，
不会把照片拉到荒腔走板。界面上显示的名字就是「整图」和「铺满」——
这两个词**作为命名**一处都没出现 —— 界面上叫「整图」「铺满」；它们只在
「解释为什么不这么叫」的语境里被引用过（就是本节上面那两段）。

## 二、几何

全部落在 `PhotoDetailGeometry` 里（纯函数，`CoreGraphics` + `Foundation`，可独立断言）。
输入三个量：视口尺寸、照片宽高比、模式。

```
isWider = 照片宽高比 >= 视口宽高比        // 照片比视口"更宽"时，宽度才是限制项

mode = fit  ┬ isWider → (视口宽, 视口宽 / 比例)     // 宽度贴边
            └ ¬isWider → (视口高 × 比例, 视口高)     // 高度贴边
mode = fill ┬ isWider → (视口高 × 比例, 视口高)     // 高度贴边
            └ ¬isWider → (视口宽, 视口宽 / 比例)     // 宽度贴边
```

四组分支的判据只有两个（取 `min` 还是 `max`、照片比视口宽还是高）。
当**照片比例恰好等于视口比例**时四组结果完全相同 —— 那种照片两种模式没有区别，
也就没有黑边可消。这一条在截图上被实测过（瀑布流的第 17 张是 16:9，
`detail=17` 与 `detail=17:fill` 两张截图逐点误差 ≤ 1）。

其余三个导出量：

| 量 | 公式 | 用途 |
| --- | --- | --- |
| `centeredOrigin` | `(视口 − 照片) / 2` | 居中基准（可能为负，`fill` 下照片比视口大） |
| `panLimit` | `max(0, (照片 − 视口) / 2)` 逐分量 | **可平移量**。为 `0` 表示该方向不可拖 |
| `offset(for:)` | `clamp(进度, -1, 1) × panLimit` | 归一化进度 → 像素位移 |

`panLimit` 取一半是因为"从居中位置到两端各有一半行程"：照片高 117.6、视口高 84 时，
上下一共多出 33.6，从居中可以各走 16.8。

**归一化进度的意义**：手机端只知道手指走了多少，**不知道外接屏多大**
（1080p / 4K / 模拟器 letterbox 窗口尺寸差异巨大）。所以手机端送的是进度，
像素行程在渲染侧算 —— 与 `ScrollMetrics` / `LateralMetrics` 同一条规矩。

## 三、交互

| 动作 | 手机端入口 | 外接屏响应 |
| --- | --- | --- |
| **单击**（幕墙页） | 触控板轻点 / 空鼠扳机 | 指针命中的那张卡 → 进详情。空白处不动 |
| **单击**（详情页） | 同上 | **什么都不做**（见下） |
| **双击** | 同上，两次轻点间隔 ≤ 0.32 s | `整图 ↔ 铺满` 切换 |
| **上下拖拽** | 单指 / 双指滑动 | 照片纵向平移（`fit` 模式下无可平移量，因此不动） |
| **左右拖拽** | 同上 | 照片横向平移（仅在照片比视口更宽时可达） |
| **返回按钮** | 指针落在左上角浮动圆上再轻点 | 退出详情，回幕墙 |

### 详情页里的单击为什么刻意什么都不做

它必须为双击让路。若单击去做别的事（比如直接退出详情），双击的第一击就会先生效，
第二击再切模式 —— 用户看到的会是"退出又进去"，像失灵。

同理，**模式切换时行程归零**：同一个进度值在两种模式下对应的像素位移完全不同，
留着它会让照片"跳"到某个奇怪的位置。

### 双击判定放在哪

`TapSequence` 是一个独立的纯值类型，**只吃时间**。原因是双击天然**跨会话**：
两次轻点分属两次「按下 → 抬起」，中间隔着一次完整的状态机复位，而
`PadGesture` 每次会话结束都会 `reset()` 清空自己的全部状态 —— 时间戳留在那里会被一起清掉。
留在视图里则完全无法断言（`simctl` 没有触摸注入 API，而本工程把"能脚本化验证"当硬指标）。

判定点落在 `RemoteControl.tap()`，因为「确认」这个动作有**三条**入口，它们都汇聚到那里：

- 触控板 / 空鼠栏的轻点（`PadGesture` → `.tap`）；
- 空鼠的扳机按钮（`AirMouse.trigger()`）；
- 触控板面板上的「轻点」兜底按钮。

判定若放在手势层，后两条路就永远双击不起来 —— 而空鼠用户快速按两下扳机
恰恰是最自然的"放大"手势。

### 连击不会连锁配对

配对成功时清空待配对状态，所以：

| 输入 | 判定 |
| --- | --- |
| 点一下 | 单点 |
| 快速两下 | 单点、**双击** |
| 快速三下 | 单点、**双击**、单点 |
| 快速四下 | 单点、双击、单点、**双击** |

不清空的话三连击会变成「单点、双击、双击」= 连切两次模式 = 最后什么都没变。

时间源被调整（系统校时、时区变更）时打出的负间隔也不算双击 —— 那不该被读成
一次"极短的双击"。

## 四、拖拽：手机端夹不住的那一半

**手机端做的夹取是保守的**：只保证进度落在 `-1...1`。真正可达的范围取决于
照片宽高比、视口尺寸与查看模式 —— 三者都在渲染侧。

于是有一个会很明显的错法：`fit` 模式下两个方向的 `panLimit` 都是 `0`，
而手机端已经把纵向进度累积到了 `1`。用户反向拖动时，先要把这 `1` 消化掉画面才会动 ——
表现得像**卡住**。

解法是**渲染侧每帧夹一次并回写**（`PhotoDetailView.onChange(of: pan)` →
`PhotoDetailGeometry.clamped(_:)` → `RemoteControl.setDetailPan(_:)`）。
回写是**幂等**的（夹取过的值再夹一次不变），因此不会形成更新循环。

这与"过卷被阻尼吃掉的那部分不该在回拉时变成凭空多出来的滚动"是同一个道理
（见 `RemoteControl.position`）。

`setDetailPan` 是本类里**第二条**「外接屏 → 模型」的写入，
第一条是卡片命中写回 `selectedItemID`。两条都由渲染侧的几何决定，
手机端算不出来。

## 五、照片宽高比是从哪来的

工程里**没有真实图片资源** —— 瀑布流卡片本身也是渐变占位。所以照片的宽高比
是造出来的，走 `WaterfallItem.aspectRatio` 这个字段，作为接真实相册数据源的接口：
接进来之后把 `PhotoDetailView` 里的渐变层换成 `Image`，几何一行都不用改。

`aspectRatio` 与 `heightWeight` 必须是**两个**字段，不能合并：

- `heightWeight` 描述**卡片在墙上占多高** —— 那是幕墙排布的结果，一张横构图照片
  完全可以被排成一根竖条（那正是"错落"的来源）；
- `aspectRatio` 描述**照片本身什么形状** —— 详情页按它决定两种适配怎么算。

合成一个值的话，详情页会把"卡片被排布拉长"误读成"照片是竖的"，
于是所有长条卡进去都变成竖构图照片。

取值是**离散档位**（`photoAspectRatio(forRoll:)`），不是连续随机：真实照片的比例
本来就是那几种（相机 3:4 / 2:3 / 16:9、手机竖拍 9:16），连续取值会造出一批现实中
不存在的比例，而且档位让断言可以精确比对。

| 档位 | 累计概率上界 | 占比 |
| --- | --- | --- |
| 3:4 | 0.36 | 竖构图合计 **70%**（相册常态） |
| 2:3 | 0.60 | |
| 9:16 | 0.70 | |
| 1:1 | 0.85 | 方图 15% |
| 4:3 | 0.93 | 横构图合计 15% |
| 3:2 | 0.97 | |
| 16:9 | 1.00 | |

### ⚠️ 抽这个随机数必须用**独立**的随机源

`demoItems` 的 36 张卡共用一个 `SeededGenerator`。所以**无论把宽高比插在卡中间、
还是追加在卡末尾，每张卡都会多消耗一个随机数**，从第 2 张开始整个序列顺移一位，
于是每张卡的高度与配色全变 —— 逐状态截图的基线整体失效，而症状只是
"截图和上次不一样"，极难定位。

「追加在序列末尾就不会动到别人」是个**看起来对、实际不成立**的直觉：
追加在末尾只保证本张卡前面那几路不变，代价照样由后面的卡承担。
（这条是实测抓出来的：01 号卡一字未变，02 号起全部不同。）

所以照片属性走**另一条** `SeededGenerator`（种子 = 主种子 + 盐）。
主序列的消耗与改动前逐个相同，`.scratch/shots/` 的既有基线继续有效。

这条不变量现在有断言守着（`.scratch/verify/main.swift` 第 14 节）：
01 / 02 号卡的 `heightWeight`、`tone.hue`、`cornerScale` 被冻成黄金值，
再加 36 张的和值指纹。序列一错位立刻红，不必等跑完截图对比。
02 号卡的 `heightWeight` 是关键的一条 —— 序列顺移时它**第一个**变。

### 截图核对

```bash
DEV=65E2C3C1-9BDA-49A7-907F-C05AF893D6B6
BID=com.jove.externaldisplaydemo
launch() { xcrun simctl launch --terminate-running-process $DEV $BID \
    -mockExternalDisplay -dockState=expanded -remoteState "$1"; sleep 3; }

launch "detail=7"              # 3:4 整图
launch "detail=7:fill"         # 3:4 铺满（居中）
launch "detail=7:fill,pan=0:1"   # 铺满 · 行程 +1（照片顶端对齐视口顶端）
launch "detail=7:fill,pan=0:-1"  # 铺满 · 行程 −1（照片底端对齐视口底端）
launch "detail=2"              # 1:1 整图
launch "detail=17"             # 16:9：两种模式应当没有区别
launch "detail=17:fill"
```

**实测数据**（模拟器替身窗口 = 362 × 203.67 pt = 1086 × 611 px，16:9）：

| 截图 | 理论 | 实测 |
| --- | --- | --- |
| 07 整图（3:4） | 照片 458 × 611 px，居中，左右各留 314 px | 横向 374..831（458 px）✔，黑边各 314 px ✔ |
| 07 铺满 | 照片 1086 × 1448 px，纵向行程 419 px | 无黑边 ✔，三档行程画面各异 ✔，两端精确贴边 ✔ |
| 02 整图（1:1） | 照片 611 × 611 px，居中 → x 297.5..908.5 | 横沿落在 290–300 与 905–915 之间 ✔ |
| 17（16:9） | 两模式尺寸相同、无黑边 | fit 与 fill 逐点误差 ≤ 1 ✔ |

（读出的是**边框行** 319…928 共 610 行，与矩形高 611 px 差 1 行 ——
抗锯齿行未达橙色阈值。判读横向边界时才用 `probe`，它给的是逐像素色值。）

位置性的旁证：详情页里的编号（「07」）与文案（「精选合集 / 3:4」）**随照片一起位移**。
所以行程 +1 时照片顶端对齐视口顶端，「07」可见而文案在屏外；
行程 −1 时反过来。这一点在截图里与几何预测完全一致。

### 工具

定位替身窗口用 `.scratch/tools/bbox`（新增）：

```bash
swiftc -O .scratch/tools/bbox/main.swift -o .scratch/tools/bbox/bbox
.scratch/tools/bbox/bbox .scratch/shots/x.png --crop 10 --out .scratch/shots/x-crop.png
```

它直接对整幅图求**橙色边框的包围盒**。为什么要新写一个而不是沿用
`docs/external-display-screenshot.md` 里的"探针逐行扫"：窗口下沿可能被遥控台压住，
那时沿橙边扫一列会在中间断掉、得到错误的高度。包围盒一次到位。

**它踩过两个坎，都写在工具注释里**（别再走一遍）：

1. 橙色判据是宽松的，手机端遥控台上的橙色也会被命中 —— 直接对全部橙色像素求包围盒，
   量出来的是"橙色元素的总范围"，高度多出一大截。修法：左右边界取全体橙色的
   min/max x（遥控台不贴屏幕边），上下边界改用**整行统计** ——
   上下边框横贯整条窗口宽度，遥控台做不到。
2. 别用"左右竖带内的 y 极值"定高度：窗口四角有 20pt 圆角，16px 宽的竖带捕获不到
   最靠上/最靠下的那 19px，实测会少算 38px（570 vs 真值 610）。

修好之后对 7 张截图算出的窗口位置完全一致（1086 × 610 px = 362 × 203.3 pt，
宽高比 1.7803 ≈ 16:9）—— 这本身就是一次交叉验证。

## 七、已知空缺

1. **没有真实照片**。接入相册后 `PhotoDetailView` 的渐变层换成 `Image`，
   其余（几何、交互、状态）不变。
2. **手点未实测**。`simctl` 没有触摸注入 API，所以「轻点点进详情」「双击切换」
   「拖拽平移」这三条**入口**只能手过。本文里被验证的是「状态 → 渲染」那半条，
   以及双击**判定逻辑**本身（纯函数断言）。手势有没有被 UIKit 收到属于既有空缺，
   见 `docs/external-display-screenshot.md`。
3. **没有过渡动画**。进出详情是硬切。要不要做一个"从卡片位置放大到整屏"的转场，
   属于观感问题，需求没提，没做。
4. **没有捏合缩放**。目前只有"整图 / 铺满"两档。中间档位（自由缩放）需要
   一个连续的缩放量，与双击的离散切换是两套东西，需求没提。
5. **多张照片之间不能翻页**。详情页固定看一张，返回幕墙才能换。
