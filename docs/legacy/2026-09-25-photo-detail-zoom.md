# 照片详情页：整图 / 铺满 + 双击 + 拖拽

> 分支 `feat/photo-detail-zoom`。需求两条：遥控台操作区放大、瀑布流 item 进详情后
> 双击放大 / 拖拽 / 再双击还原。
>
> 结论性内容（几何、交互、验证数据）在 [`docs/photo-detail.md`](../photo-detail.md)。
> 这篇只记**过程与踩坑** —— 特别是三个"看起来对、实测不成立"的直觉。

---

## 0. 先对齐口径，再动手

需求原话是「默认高度 fit，双击实现 width fit」。动手前先画了两张几何图 + 一张路由图
确认理解，图上显式标了三处假设：

1. 双击的第二击已经落在详情页上（第一击才负责"进详情"）；
2. 详情页里的单击是 no-op；
3. 返回按钮在详情页里是"退出"。

同时提出把「height fit / width fit」改成「整图 / 铺满」（`min` / `max` 缩放）。
理由是竖构图照片在"宽度适配到底"下会被拉成 2.37 倍视口高的竖条。
用户回复「可以按照专业产品经理进行描述」，口径据此定案。

**这一步值得单独记**：口径定错的话，后面所有的几何、断言、截图判据都要重写一遍。
图上那三处假设也各自变成了后来的一条代码注释。

## 1. 三个"看起来对、实测不成立"的直觉

### 1.1 「新增随机量追加在序列末尾就不会动到别人」—— 不成立

`WaterfallItem.make` 里新增第八路随机量（照片宽高比）。当时按"追加在末尾"写，
以为既有的七路取值会一字不变。

写完跑了基线对比（`.scratch/tools/baseline-check`，把 HEAD 版与工作区版各编译一次、
各自打印 36 张卡的全部随机量、`diff`）：

```
2,36c2,36        ← 01 号卡一字未变，02 号起全部不同
```

根因：36 张卡**共用一个** `SeededGenerator`。追加在末尾只保证**本张卡内部**
前面那几路的字段顺序不变，但每张卡照样多消耗一个随机数 ——
代价由**后面的卡**承担，从第二张起整个序列顺移一位。

修法：照片属性走**另一条** `SeededGenerator`（种子 + 盐）。主序列的消耗与改动前
逐个相同，基线继续有效。

**教训**：`diff` 输出的形状本身就是线索 —— "01 相等、02 起全变"精确指向
"每卡多消耗一个随机数"，而不是"某一路算错了"。如果只看到"截图和上次不一样"，
几乎不可能定位到这里。

这条不变量后来被冻成断言（`verify` 第 14 节），02 号卡的 `heightWeight`
是关键的一条：序列顺移时它第一个变。

### 1.2 「恰好等于窗口算双击」—— 在 `Date` 上不可复现

断言 `registerTap(at: base + 0.32)` 应当返回 `.double`（判定是 `interval <= 0.32`），
实测返回 `.single`。

`Date` 内部是量级约 7.7e8 秒的 `Double`（本用例里 `base = 1000`，量级小一些，
ULP 约 1.1e-13），两个相近时刻相减只剩十来个有效位。
`0.32` 这个字面量本身要 2⁻⁵⁴ 的粒度才表达得准，而相减的结果只能落在 2⁻⁴³ 的格子上 ——
四舍五入到上侧，就变成了 `0.3200000000000001 > 0.32`。

**这是浮点噪声，不是逻辑问题。** 断言一个由浮点噪声决定的结果毫无意义，
所以改成从两侧逼近：窗口上界**内侧差 1 微秒**算双击、**外侧加 1 毫秒**不算。
余量取 1 微秒是刻意选的 —— 比该量级下的 ULP 高一个量级，
又远小于任何人类可感的双击间隔差异。

（第一次尝试用了 `- 1e-9`，小于 ULP，会被四舍五入到同一个值，照样失败。）

### 1.3 「断言里可以直接写死期望值」—— 差点把错误固化

几何断言有一条写的是：

```swift
checkClose(wideFill.panLimit.height, (1620 - 1080) / 2, 1e-6, "铺满：纵向行程 = (照片高 − 视口高)/2")
```

`1620` 是 `fit` 模式下的照片**宽**（3:2 照片按 1080 高贴边），被误当成了
`fill` 模式的照片高。`fill` 下照片是 1920 × 1280（宽度贴边），行程该是 100。

**期望值必须从同一份几何里推导**，不能手写：

```swift
checkClose(wideFill.panLimit.height,
           (wideFill.photoSize.height - detailView.height) / 2, ...)
```

写死数字的断言在几何改动后还会"继续绿"，或者像这次一样报出假的失败 ——
两种都坏，只是坏法不同。

## 2. Swift 编译器的类型检查超时（三次）

`PhotoDetailView` 的 `photo(geometry:)` 里那条修饰符链（`ZStack` 三子视图 +
`clipShape` + `overlay` + `shadow` + `offset`）连续三次编译失败：

| 次序 | 报错 | 处理 |
| --- | --- | --- |
| 1 | `unable to type-check this expression in reasonable time` | 把两个渐变端点色抽成属性、`glow(size:)` 抽成方法 |
| 2 | 同上 | 全部尺寸常量改显式 `CGFloat` 局部量 |
| 3 | `failed to produce diagnostic for expression; please submit a bug report` | 拆成 `let stack` / `let clipped` / `let bordered` 三段**显式类型**局部量 |

根因是 Swift 把整条链当成**一个**表达式求解：字面量的数值类型要参与重载决策，
链一长解的搜索空间就爆。显式标注之后每个子表达式只剩一种解，编译瞬间就过。

**可复用的判据**：报错落在 `.offset` 这一层、且错误信息退化到
"failed to produce diagnostic"时，不要再怀疑某个具体修饰符 ——
是整条链太长，直接分段。

## 3. 一个低级错误，但值得记

`PhotoDetailGeometry.offset(for:)` 返回 `CGSize`（与 `LateralMetrics` 同一口径，
断言脚本也用 `.width` / `.height`），视图里却写成了 `.x` / `.y` ——
`CGSize` 没有这两个成员，报 `value of type 'CGSize' has no member 'x'`。

从摘要恢复上下文时，这类"上一轮改到一半"的错误最容易漏。
处理顺序定为：**先让编译过，再谈验证** —— 编译不过时跑出来的 `verify` 二进制
是旧的那一份（303 条），结果看着"全绿"其实一个字没验。

## 4. 截图核对：为什么新写了一个 `bbox` 工具

`docs/external-display-screenshot.md` 给的是"探针扫一条穿过窗口的列/行，读四条边的像素坐标"。
这次直接套用就出错了：窗口下沿被遥控台压住，沿橙边扫一列在中间断掉，
算出来的高度是错的（538 px，实际应是 611 px）。

于是写了 `.scratch/tools/bbox`：直接求**橙色边框像素的包围盒**，一次到位。

它的橙色判据是宽松的（红显著高于绿、绿显著高于蓝），所以手机端遥控台上的橙色
也会被算进去 —— 使用时要看输出的"窗口内区"那一行，而不是包围盒本身。
这个局限写在工具头部注释里了。

**替代品不划算的证明**：试过用 `probe px` 逐点读，能读准，但要先把边界猜出来才读得对 ——
而"猜边界"正是要解决的问题。

## 5. 验证结论

- 断言：`.scratch/verify/main.swift` 从 303 条增至 **366 条，零失败**。
- 基线：36 张卡的高度与配色与 HEAD **逐位相同**（改造后重跑 `diff` 无输出）。
- 截图：7 张状态截图，几何与理论值逐项吻合（数据表见
  [`docs/photo-detail.md`](../photo-detail.md) 第六节）。

三条没被验证的（`simctl` 无触摸注入 API）：**轻点进详情**、**双击切换**、
**拖拽平移**这三条入口只能手过。被验证的是「状态 → 渲染」那半条，
以及双击的**判定逻辑**本身。
